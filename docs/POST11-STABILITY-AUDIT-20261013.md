# .11 后续稳定性排查

基线为 `7165b52c`；桌面和双人测试仍使用源码 `99b7ce4b` 的 `.11`。
本轮是源码修复与隔离回归，不替换测试包、用户数据，不修改生产服务或运行 ET/TUN。

## 已复现的问题

1. **认证重试被健康观测取消。** 有效 ET 会话上刷新 bearer，认证请求暂时失败后，
   后续 `connected` 观测误取消认证重试。核心在线不代表新令牌已经认证。
2. **失败后丢失旧会话比较依据。** 同一错误路径删除先前成员记录，后续认证范围
   改变时，runtime 已关闭旧核心，manager 却不能识别需要重建。
   并发回归另确认：前一次认证已经改变范围，但被后一次更新取代，前者跳过
   manager 重建；后者认证返回范围未改变，也跳过重建。需要保留未完成的
   manager 替换责任，只允许当前仍有效的期望成员消费，移除/关闭应清除。
   另检查替换已完成、调用方随后过期的窗口：先按对象身份清除已完成的旧责任，
   防止下一次同范围认证再重启核心，不清除其他尚未完成的新责任。
3. **恢复相同接收权限复用旧协商记录。** 权限 A→空→A 后，仍保留旧 committed key；
   新 offer 的 `ontrack` 可在新 answer 完成前通过接收检查。测试证明的是协商
   门槛缺口，不是当前已撤销权限下的越权，也不是真实有声证明。
4. **SDK 重新启用遗留停止中的控制器。** `setEnabled(false)` 的 SFU 恢复失败后
   再启用，旧控制器保留 stopping 状态，不再监控失效 peer 或自动回退。当前产品
   策略固定 enabled=true，此项属于 SDK 边界回归，不宣称日常路径必现。
5. **三种错误原因丢失。** `peer_path_inconsistent`、`invalid_receive_candidate`、
   `invalid_receive_node` 经客户端诊断转换变成 `other`，无法区分实际恢复原因。

## 修复边界

待认证状态与核心健康观测分离；保留旧已验证成员作为会话比较和清理责任，
不赋予新令牌授权，也不改变 runtime 的 TTL、撤销与身份验证规则。
权限变化使旧协商完成记录失效；重新授权仍需当前 answer，保留其他正常接收流。
控制器开始停止后，重新启用也必须先完成 SFU 恢复和旧控制器退役，再创建新控制器。
日志增加上述三个固定枚举，不增加身份、地址或自由文本。
